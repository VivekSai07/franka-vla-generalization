# Failures and lessons

Every failure that cost real time, with the fix and the commit. The actionable
pre-launch version is the checklist in
[.github/skills/launching-a-run/SKILL.md](../.github/skills/launching-a-run/SKILL.md).

Published datasets/checkpoints for these experiments: [HF artifact index](HUGGING_FACE_ARTIFACTS.md).
Hash-bound READMEs and historical reports are linked from that index without changing their bytes.

## Failures we hit (and what we learned)

1. **Expert failure counted as stop** — first broad_workspace run halted at 52/200 because a failed expert bubbled up as a hard error. Fix: wrap in `ExpertRejection`, bill to rejection budget (`57975c5`).
2. **Deleted the pilot manifest** during cleanup, breaking every downstream `provenance()` check. Fix: make manifest optional in `fixed_layout/source.py` (`57f558d`), then re-seal `local_varied_data` with post-surgery provenance and update `SEAL` constants (`f3f3244`).
3. **X-VLA reload verify used CPU + no autocast** — checkpoint verification hit `Input cuda / weight cpu` because obs came from the CUDA training path but the reloaded policy stayed on CPU. Fix: `.to('cuda')` + `torch.autocast('cuda', bfloat16)` in `_reload_and_verify` (`391049c`).
4. **LeRobot per-episode PNG staging accumulated across rejections** — rejected ep 52's 528 PNGs stayed under `episode-000052/`, so ep 53's writes gave 1056 files → encoder coverage check tripped. Fix: purge staging PNG dir + reset `episode_buffer` after every `ExpertRejection` (`4561995`).
5. **Attempts dir naming diverged from LeRobot's episode_index after rejections** — encoder read ticks from `attempts/000052/` (rejected) while PNGs came from ep 53. Fix: expose `dataset._active_attempt_path` set in `record_attempt`, use it in the encoder wrapper (`2435dca`).
6. **Validator hard-coded `slot['episode_index']+1` as expected admit count**, which no longer matched LeRobot's `total_episodes` post-rejection. Fix: read `info.json['total_episodes']` as the count and let the remaining `_metadata` invariants (schema, task, fps, frame count) do the checking (`3d733d2`).
7. **Preflight scratch dir deleted** to free disk before eval → `verify_final` couldn't hash `SCRATCH/result.json`. Fix: make scratch check conditional in the eval package (`c8a6904`). The preflight `result.json` had non-deterministic timing fields so it wasn't reproducible.
8. **Editing source files while eval was still running** → final `c.admission()` re-check saw drift and marked the run "failed" even though all 92 rollouts had already completed cleanly. Lesson: freeze the code path for the duration of the eval.
9. **Rejections skipped the slot instead of retrying it** — this was the root cause behind three separate 35-hour collection failures at the same point. Slot index doubled as the admitted-episode index, and `metadata[i]`, `attempts/{i:06d}`, `resets/episode_{i:03d}` and the train/val split boundaries all depend on `slot == admit`. Skipping broke every one. Fix: retry the same slot until admitted (`3926614`).
10. **The tests asserted the buggy behaviour.** 35/35 passed while production died three times identically, because `test_expert_execution_failure_billed_to_rejection_budget_not_stop` demanded `len(admitted) == 198` — i.e. it *required* slots to be skipped. Rewrote the tests to assert correct behaviour and added a regression test that runs `validate_journal` over scheduler output. Green tests are not evidence when they encode the defect.
11. **Two layouts were physically uncompletable / irreproducible.** `validation_020` failed all 16 expert attempts (cube 2.0–2.1 cm off, admitted episodes ≤1.74 cm). `validation_032` stacked fine but its grasp geometry made the float32 replay drift 1.51e-3 (tolerance 1e-3) *identically on every redraw* — variance <1e-8 across independent ±1° jitters, proving it systematic rather than chaotic, so no amount of redrawing could fix it. Fix: deterministic layout resampling inside the same envelope (`76d8e91`, `c429b1d`). Both fall in the validation split, so the 160 training episodes are untouched.
12. **Resume, rollback and unique rejected paths** — a crash at 179/200 would have discarded everything. Added `resume_state` + `amend_frozen_plan`, episode rollback with stats re-aggregation for drift rejections (`91cc4cf`), and unique `rejected/{i}_k{k}_r{n}` paths after a rename collision killed a run (`7807c7c`).
13. **The evaluation inherited pilot-era workspace bounds.** `restore_scene` gates on `pilot_integrity.validate_scene_geometry`, which caps |y| at 0.40 m — but envelope F7 reaches 0.45 m. Scene derivation was provably correct (every per-array SHA256 matched the sealed bank) yet 12 of 36 holdout layouts were rejected, precisely the widest and most discriminative ones. Relaxing the shared validator would have invalidated the sealed provenance of every dataset, so the eval packages restore with the collector's own F7 geometry gate instead (`e11c784`).
14. **A holdout failure is not automatically a policy failure.** The 80 reserved layouts were never expert-verified, and 8 of them failed X-VLA on both seeds — indistinguishable from an unsolvable layout. Screening all 8 with the scripted expert showed every one is solvable, which is what makes 68.1% reportable. Do this screening before reporting any systematic failure cluster.

15. **The runner hardcoded the training horizon separately from the contract.** `recipe()` was changed to 16700 updates and every contract test passed, but `runner.py` had its own `maximum = 2 if preflight else 5000`. The run trained exactly 5000 updates, wrote checkpoints `[1, 2000, 4000]`, and only failed *afterwards* on `verify_checkpoints` — ~70 min of GPU wasted. The tests missed it because contract tests asserted `recipe()` while runner tests used synthetic checkpoint fixtures; nothing tied the loop bound to the recipe. Fix: derive `maximum` from `c.recipe(False)['max_optimizer_updates']`, plus a regression test asserting the runner contains no `else 5000` and that horizon / final checkpoint / LR-schedule total all agree (`4f7d621`). **Verify such a test actually fails against the pre-fix code** — this one was checked with `git stash`.
16. **Editing any `SOURCE_FILES` member invalidates the recorded admission.** Fixing `runner.py` meant the relaunch correctly refused with "Current full CPU admission required", forcing a ~1h re-`--check` and a fresh `--preflight`. Not a bug — the gate working — but budget for it: a one-line runner fix costs a full admission cycle.
17. **A hash-bound README nearly killed a finished 3-hour evaluation.** `broad_workspace_data/scenes.provenance()` explicitly appends its own README (`paths += [Path(__file__).with_name('README.md')]`). Editing it to mark collection complete would have failed the eval's final `c.admission()` after every rollout had already succeeded. Caught and reverted; provenance and binding re-verified. **Consequence: that README, and `experiments/{xvla,smolvla}_local_varied/README.md`, can never be corrected** — the latter two permanently state seal `f8b10a49…` when the actual is `ae8828ea…`.
18. **A stale `git worktree` silently ran old code.** The historical-source worktree used for cross-evaluation was created at an earlier commit, so it kept executing a superseded `c.admission()` path long after the fix was committed — presenting as a logic bug. It also could not simply be refreshed, because another run was live from that same mount. Check `git log -1` inside a worktree before blaming the code.
19. **Long-running jobs were left unmonitored.** A training run failed and sat dead for 47 minutes because completion was assumed rather than checked. `docker wait` has also silently failed to notify in this environment. Poll actively at each stage; do not treat "launched" as "will report". Fixed structurally by chaining train → verify → evaluate in one detached host script that refuses to start the evaluation unless the training report verifies.
20. **An evaluation package was hard-bound to one training run.** `xvla_broad_workspace_eval` pins `completed_updates: 5000` and validates `--checkpoint` against the short run's schedule, so it could not evaluate the matched-exposure run at all — it would have aborted at the first gate. Forking it was correct (`2c7a90c`), but two traps came with the copy: the horizon had to be *derived* (`recipe(False)['max_optimizer_updates']`, asserted against `checkpoint_updates(False)[-1]`) rather than re-hardcoded, and the copied tests still imported the **old** module, so they passed 26/26 while testing entirely the wrong code. That is meta-lesson #1 for the fifth time.
21. **Offline metrics do not predict task capability — they actively mislead.** On the matched-exposure run, train/val arm MAE improved monotonically (0.03390 → 0.02621 → 0.01022) while rollout success went 25.0% → **0.0%** → 86.1% on the identical holdout. At update 8,000 the policy still grasped 72/72 but lifted only 17/72, leaving the cube a median 63 cm from target — a total capability collapse invisible in the loss, the MAE and the gripper accuracy. Never select checkpoints, stop early, or report progress from offline probes. Only rollouts count. Corollary: mid-training checkpoint evaluations are not a cheap substitute for the endpoint, and a val/train ratio is not by itself an overfitting signal.
22. **A predicted control turned out not to be a control.** The matched-exposure run was given a checkpoint at update 4,000 specifically to compare against the short run's 4,000 and isolate LR-schedule effects from exposure. It does not: at that update the short run sits at lr 2.05e-5 (80% annealed) and the long run at 9.00e-5 (24% annealed), so the pair compares different schedule phases and is unsurprisingly indistinguishable (15/72 vs 18/72, p = 0.69). The LR-matched pair is short@4000 against long@12000 (2.74e-5), which resolved it decisively: 20.8% vs 70.8%, p = 2.2e-9. Lesson: when matching runs for a comparison, match the *schedule phase*, not the raw step count — checkpoint schedules should be chosen from the LR curve, not from round numbers.
23. **A plausible root-cause hypothesis, refuted by data.** The 10 remaining failures at 86.1% are a placement offset of roughly one cube width — cube set down beside the target rather than on top. The natural explanation was that the policy imitates an imprecise expert. Checking all 200 sealed demonstrations refuted it outright: expert mean final error 0.679 cm, max 1.981 cm, **zero** episodes above 2 cm, mean signed offset 0.1 mm, and a correct stack height in 200/200. The offset is policy-side. Recorded because the hypothesis was reasonable, cheap to test, and wrong — and because it changes the plan: more episodes of the same kind should not be expected to fix it. A second intuition died alongside it: the failures were assumed to be far, hard-to-reach layouts, but failing layouts average 0.424 m reach against 0.472 m for fully-solved ones — the far layouts are solved. A third, coverage density, died too: 4-D nearest-neighbour distance to the training layouts is identical for both groups (0.0348 m) with rank correlation τ = 0.000.
25. **A between-layout spread was reported as within-layout precision.** The 10 failures were described as "4.51 cm ± 0.20 cm — 2 mm consistency across ten independent trials", which sounded like a tightly controlled systematic bias. But those 10 trials came from **8 different layouts**, one or two each, so sd 0.20 cm measured variation *between layouts*, not the sampling variability of the policy. Re-measuring one layout across 8 seeds gave a spread several times larger, and the 128-trial run settled it: failures are +3.893 cm with sd **0.723**. Two further claims from the same small sample also failed: "9 of 10 land toward the robot base" (there is no global radial bias — successes sit at +0.15 cm once control layouts are included) and "a systematic offset" (it is layout-specific; control layouts never produce it at all). **Lesson: before calling a spread tight, check how many independent units it was computed over.** A statistic pooled across groups describes the groups, not the units inside them.
24. **A forked package kept a reference to machinery the fork deleted.** `xvla_placement_modes` removed the fixed-parity path but left `if resume_fixed_parity_only:` in `run()`, so the job died with `NameError` one minute in — after claiming the GPU and creating its output directory, which then blocked the rerun by the no-overwrite rule. **36 tests passed against this**, because none of them drive `run()` past its overwrite guard; the roster, summary, CLI and binding were all verified while the only code path that matters was never executed. Fix: delete the dead branch, plus two regression tests — a `symtable` scan asserting no function reads a name that is never bound anywhere in the module, and a check that no fixed-parity identifier survives in `run()`. Both were confirmed to fail against the unfixed file via `git stash`. The `symtable` check is worth copying into any future fork: it catches this entire class of bug statically, in milliseconds, without a rollout.

26. **A test sweep reported seven failing packages; five were harness artefacts and the rest were pre-existing.** Running every package with `outputs` mounted read-only produced `OSError: Read-only file system` in three packages that legitimately need `outputs/implementation/<name>/` writable — `broad_workspace_data`, `local_varied_data` and `local_position_probe` all go green once mounted (see [OPERATIONS.md](OPERATIONS.md)). An initial grep for `mkdtemp(dir=...)` found only two of the three dirs, so the third was still failing after the first correction. The remaining failures (`fixed_layout`, `single_task`, `xvla_single_task`, `smolvla_fixed_layout`, `smolvla_local_varied`) are downstream of the deleted pilot manifest (#2) and **fail identically or worse on `main`** — 9 errors there against 4 on the branch for `xvla_single_task`. **Lesson: a red suite is no more self-evident than a green one.** Before treating failures as a regression, reproduce them on the base branch in a worktree and compare counts; one `git worktree add` showed the branch strictly reduced every count.

27. **The dataset made colour non-diagnostic, and nobody noticed for 200 episodes and four training runs.** `plan.py` samples the pick cube from y ∈ [−0.45, −0.20] and the place cube from y ∈ [+0.20, +0.45] — disjoint regions 40 cm apart, in 200/200 episodes and 80/80 reserved evaluation layouts. The pick target is therefore perfectly predictable from `sign(y)`, so a policy that never perceives colour and never reads the instruction can score 100%. Every result to date, including 86.1% on the broad holdout, measures spatial capability only. Worse, the planned language test — *reverse the instruction over the same layouts* — would have made "red→green" ≡ "pick −y" and "green→red" ≡ "pick +y", letting a colour-blind model score 100% and be reported as evidence of grounding. Caught during B1 design, before any collection; the fix is to decorrelate colour from position (2×2 factorial, see the B1 spec). **Lesson: when a dataset holds a nuisance variable constant, any capability that correlates with it becomes untestable — and the shortcut is invisible in the success metric.** Before claiming a model uses some input, check whether the data ever made that input necessary.

28. **The shared validation stack is single-task throughout, and it is hash-bound.** B1 needs two instructions. `experiments/fixed_layout/validate.py` assumes exactly one in **five** places: `read_rows` requires every frame's `task_index` to be `0` (line 89); the frame check requires `raw["task"] == TASK` (257); `_metadata` requires `total_tasks == 1` (422), `tasks.index == [TASK]` (435) and `ep["tasks"] == [TASK]` (443). Three of those were overridden by a local `metadata()` in the B1 package, but the other two sit inside `read_rows` and `_episode_inputs`, which the B1 code calls through. **The file cannot be edited**: `fixed_layout/source.provenance()` does `paths += sorted(Path(__file__).parent.rglob("*.py"))`, so `validate.py` is inside the sealed provenance of `broad_workspace_data` — confirmed by reading `provenance.json`, which lists all 12 `fixed_layout` files. Editing it would invalidate the sealed 200-episode dataset and every result bound to it, including 86.1%. **Lessons:** (a) before designing a dataset variant, grep the *shared validation* path for assumptions about the thing you are varying, not just the collection path — the expert and the plan supported two instructions from the start, and the blocker was three layers down; (b) a shared module being hash-bound converts "edit one constant" into "duplicate the validator or re-seal everything"; (c) three collection launches died at 3 min, 1 min and 3 min, each on the next single-task assumption in sequence. Fixing them one at a time was the wrong strategy — one `grep` for the varied concept across the whole call path would have found all five at once.

29. **The same shared validator is also hardcoded red-on-green, one layer below the single-task assumptions.** After #28's five task-related assumptions were overridden, the sixth launch failed in three minutes with `{'closed_ticks': 240, 'bilateral_ticks': 0, 'contact_lift_m': 0.0}` — the gripper had closed, but the *red* cube never moved, because on a C3 episode the expert had correctly picked the **green** one. `fixed_layout/validate.py` binds the cube pair in four more places: `contact_gates` hard-rejects any pair that is not `("red", "green")` (line 146); `_observation` binds `pick_xyz`/`place_xyz` to `target_cube_red`/`target_cube_green` (177–178); both `contact_gates` call sites pass the red body's height as the lift reference (293, 384); and `stack_metrics` is called with colour literals (298) even though that helper is colour-generic everywhere else in the repo. The fix rebinds five module globals per episode through a `task_aware` context manager rather than editing the sealed file. **Lessons:** (a) the #28 lesson — "grep the shared path for assumptions about the thing you are varying" — was applied to *instructions* but not to the **consequence** of changing the instruction, which is which physical object gets manipulated; the grep should have been for the varied concept's downstream effects, i.e. `target_cube_`, not just `TASK`; (b) five launches died at 1–3 minutes, each on the next assumption in sequence, and the sixth was only avoided by stopping to enumerate *all* colour bindings at once before writing any more code; (c) a 2-episode boundary-crossing smoke test would have caught every one of these in three minutes instead of six launches — the B1 plan puts C1/C3/C2/C4 at episodes 0/1/3/4, so the first ten minutes of the real run exercises all four cells and is itself the smoke test. **Design the episode order so the riskiest case runs first.**

30. **One layout in 280 was unsolvable by the expert, and it killed a 6.5-hour collection at slot 197/200.** After 197 consecutive first-try admits, slot 197 (cell C3, green-on-red, layout `validation_037`) was rejected nine times — once per feasible home-pose redraw — every time with reason `expert_execution`, and the collector raised `Slot 197 exhausted every feasible draw without an admitted demonstration`. All nine rejections in the entire run were on that one slot. The scripted expert simply cannot complete a stack on that geometry, the same class of hard layout T2a characterised. Recovery used the collector's designed escape hatch: `INFEASIBLE_LAYOUT_RESAMPLES = {'validation_037': 0}` plus `--resume`, which unlinks `failure.json` and calls `amend_frozen_plan` to substitute *only* that layout, rewrite plan/bank/provenance/snapshots, and preserve the superseded provenance in `amendment.json`. All 197 collected episodes were kept; slots 197–199 then admitted first try, giving a balanced 50/50/50/50. **Lessons:** (a) the mechanism only works because `amend_frozen_plan` refuses unless *no already-collected attempt depends on the moved layout* — verify that (here, exactly one episode used `validation_037`) before amending, or the recovery silently invalidates collected data; (b) a resampler inherited from a fork may be keyed to the old parameterisation — `resample_layout_xy` had to be region-aware after the 2×2 rewrite, and would have produced colour-envelope draws otherwise; (c) with a ~1/280 per-layout infeasibility rate, a 200-slot run has a substantial chance of hitting one, so the escape hatch should be treated as an expected step, not an exception. **A failure at slot 197 of 200 costs the same wall-clock as a failure at slot 1 if the run cannot resume — the resume path is the feature that matters.**

31. **Preflight checkpoints are part of the evidence chain, not scratch — deleting them to free disk broke training.** The B1 training run aborted on `require_disk(output, 60)`, a guard inherited from `xvla_broad_workspace_long`, which was sized for that package's 9-checkpoint schedule (measured: 8 x 3.3 GB + 9.9 GB final = 37 GB). B1 writes 5 checkpoints (23.1 GB), so the guard was genuinely wrong and was lowered to 30 GiB. Bundled with that correct fix was an incorrect one: the chain deleted `<run>_preflight/checkpoints` after preflight passed, on the assumption that a 2-update smoke test is disposable and its 14 GB was wasted headroom. Training then died instantly with `FileNotFoundError: .../_preflight/checkpoints`, because `train()` calls `validate_scratch(...)` → `verify_checkpoints(report, SCRATCH, True)` and **re-audits the preflight checkpoints as a precondition**. **Lessons:** (a) in a contract-bound pipeline, every artifact a stage writes is presumed to be evidence unless proven otherwise — grep for the path before deleting anything, because "obviously temporary" output is exactly what a later stage re-verifies; (b) do not bundle a speculative optimisation with a necessary fix — the disk guard change was right and the cleanup was wrong, and shipping them together made one failure look like two; (c) editing any file in `SOURCE_FILES` (here `runner.py`) invalidates a completed CPU admission and forces a 28-minute re-run, so batch such edits; (d) the recovery was to make admission reusable when `status == passed` and the tree is clean — safe because `train()` re-validates the binding against the recorded admission, so a stale one fails fast rather than silently.

32. **B2's first collection died at episode 0 because parked distractor cubes are not at rest.** Moving `target_cube_blue` and `target_cube_yellow` out of the pilot parked pose inherited that pose's residual free-joint velocity. The disturbance gate then reported both cubes about 1220.8 m from the placement (`{'blue': 1220.799199883823, 'yellow': 1220.7991998838222}`), so the slot was rejected as a replay failure rather than an expert collision. B2 is the first package to move those two bodies; every prior dataset left them parked, which is why the motion was invisible. Fix: zero the placed distractor's 6-DoF `qvel` in `scenes._rest_distractors` and reject inherited motion in `_validate_broad_geometry`, with regression tests that a placed cube starts at rest and stays within 2 cm over two seconds of physics (`b375c4f`). **Lesson: a parked pose is not a rest pose — check `qvel`, not just `qpos`, before relocating a free body.**

33. **Rolling back the first committed episode tried to reach the Hub under offline mode.** Handling that episode-0 rejection called `rollback_episode`, which deleted the only episode metadata and then built `LeRobotDatasetMetadata` to re-aggregate stats. With no local episodes left, LeRobot fell through to `huggingface.co` and raised `OfflineModeIsEnabled` (`HF_HUB_OFFLINE=1`, `--network none`). The velocity rejection therefore became a crash instead of a retry. Fix: when the rollback leaves zero episodes, delete `meta/stats.json` instead of re-aggregating through metadata that falls back to the Hub (`b375c4f`). **Lesson: the empty-dataset branch of rollback is a different path from "recompute stats from the survivors", and it is the path an episode-0 rejection actually takes.**

34. **`git switch` to a branch with a different tree crashed a live collection at episode 49, while a same-tree `git branch`/`switch` moments earlier had been correctly judged safe.** Recovering from B2's unbranched work moved five commits from `main` onto `feat/b2-distractors` via ref-only operations (`git branch`, `git switch` to an identical tree, `git branch -f main origin/main`) — genuinely safe, verified against `git status --short` being empty, and the collection kept running. A later, unrelated `git switch main` in the same session checked out `main`'s *actual* tree — now missing `experiments/b2_distractor_data/`, the B2 spec/plan docs, and the B2 `TODO.md`/`FAILURES.md` edits, since those live only on the feature branch after the reset — while the collection container still had this directory bind-mounted live. The container's per-episode provenance re-hash tried to open `docs/superpowers/plans/2026-09-28-b2-distractors.md`, found it gone, and crashed with a raw `FileNotFoundError` at episode 49 (94 minutes into the run) instead of the graceful "provenance changed" error. Recovery: `git switch` back to the branch with the matching tree (no data lost — episode 49 had already committed to the LeRobot dataset before the crash, so `rollback_episode` plus moving its `attempts/000049` to `rejected/` restored a state `resume_state` accepted, and `--resume` re-admitted it cleanly one episode later). **Lessons:** (a) "switching branches doesn't touch files" is only true when the destination tree is identical to the source — the same command is safe or destructive entirely depending on *which* branch, and that has to be re-checked every time, not assumed from the last check; (b) a repo hosting a live job needs a rule of "no `git checkout`/`switch`/`reset` on that checkout at all until the job ends," not "no *destructive* ones" — a same-tree switch earlier in the session was correctly judged safe, but the very next branch operation in the same session was not the same case, and treating the category as pre-cleared was the mistake; (c) this is exactly the failure mode [branching-for-an-experiment-axis](../.github/skills/branching-for-an-experiment-axis/SKILL.md) was written to prevent, written in the same session it was then violated in — writing a rule down does not substitute for checking it against the specific next action.

35. **A second unsolvable layout, `train_124`, hit exactly the mechanism FAILURES #30 built — and exposed a bug in that mechanism that #30 never exercised.** Slot 124 (cell C4, green-on-red, distractor-present, layout `train_124`) was rejected all 9 feasible redraws with `expert_execution`, and the collector raised `Slot 124 exhausted every feasible draw`, exactly like B1's `validation_037`. The escape hatch — `INFEASIBLE_LAYOUT_RESAMPLES = {'train_124': 0}` plus `--resume` — is unchanged from B1 and worked as designed for the layout substitution itself. But `amend_frozen_plan`'s per-episode equality check (`previous['episodes'] != plan['episodes']`) was copied verbatim from B1, which has no per-episode field that legitimately changes when a layout moves. B2 does: episode 124's `distractor_xy_m` is drawn against its own layout's cube geometry for minimum clearance, so substituting that layout's geometry correctly recomputes it — and the inherited check rejected that as if it were unauthorized drift, aborting `--resume` immediately with `ValueError('Amendment may not change any episode slot')` before any files were written (so nothing was lost; the retry was clean). Fix: the check still requires every episode to keep its `layout_id` and every other field bit-identical, but allows `distractor_xy_m` to differ **only** for the episode(s) whose layout is in `moved` (`da7542c`), with two tests updated from "no substitution has ever happened" to "exactly `train_124` moved, and only its `distractor_xy_m` differs" (`2013661`). **Lessons:** (a) copying a forked package's recovery machinery is not exempt from the fork-hygiene audit in [forking-an-experiment-package](../.github/skills/forking-an-experiment-package/SKILL.md) — an equality/invariant check written for the source package's data model needs re-checking against every field the fork *added*, not just the fields the fork's happy path touches; (b) this bug could only be found by actually hitting the recovery path, because every test written against B1's version of the check was (correctly, at the time) asserting an empty registry — a green suite here meant "the untested path was never exercised," not "the path is correct"; (c) the failed `--resume` attempt raised before writing any file, which is why it was safe to fix and retry immediately — a recovery mechanism whose validation runs strictly before its mutation is what made a code bug a non-event instead of a second data-loss incident.

36. **A forked `evaluate.py` silently did nothing, and every stage "passed" instantly on a fake result.** `xvla_b2_distractors_eval/evaluate.py` was written by adapting `xvla_b1_language_eval/evaluate.py` line by line, but the final `if __name__ == '__main__': main()` guard was dropped in the process. `python -m experiments.xvla_b2_distractors_eval.evaluate --mode=smoke --checkpoint=16700` therefore imported the module, defined every function, and exited 0 without calling `main()` at all — no MuJoCo model loaded, no checkpoint read, no rollout run, no output directory created. The launch chain (smoke → screen × 5 checkpoints) "completed" six GPU stages in 27 seconds total, each reporting `rc=0`, before failing only at the very end when the report-picking step found no `evaluation_screen_step_*/result.json` files to read. **Caught by**: the wall-clock time was implausible for a real rollout (each trial alone should take tens of seconds) — not by any test, not by the exit code, not by the chain's own gating, all of which reported success. Fix: restore the guard (`3fed6e8`); add a CPU test asserting the file contains `if __name__ == '__main__':` followed by a call to `main(` — confirmed to fail against the pre-fix commit (0 occurrences of `__main__` in the buggy file). **Lessons:** (a) `rc=0` proves a process exited cleanly, not that it did anything — this repo's own `NOTE: rc=0 is not a result` convention exists for exactly this reason, and it applies to every entrypoint, not just collection/training; (b) a module-level fork that "looks complete" because every function and docstring was carefully adapted can still be missing the one line that makes any of it execute — the fork-hygiene symtable scan (FAILURES #24) catches *undefined* names, not *unreached* code, so it did not and could not catch this; (c) a launch chain that gates stage N+1 on stage N's exit code needs at least one independent check that stage N did real work (elapsed time, an expected output file, a non-trivial log line) — exit code alone was not sufficient evidence here.

driver's resume completed the missing trials (each reseeds itself, so they equal uninterrupted ones) and nothing was
lost, but only because resume existed. Fix: pin cores per worker, size the pool by the peak (post-switch) memory rather than
the first-load figure, and treat a measured per-worker cost as valid only at the concurrency it was measured at. The cause
of the memory growth after a switch was not isolated.

58. **A validation threshold was fixed without computing what the sample sizes permit, and the validated measure was then
redefined once without that check.** P2 diagnostics (2026-10-19) defined Gate 1 as "at least 0.80 of the successes' grasps lie
inside the envelope" before looking at any failure. With the expert's envelope it read 0.225: the scripted expert grasps
far more precisely than a success needs (yaw within about ±3° for box objects against policy successes at −15° to −2°). I
amended the envelope to the other checkpoint's successes and kept 0.80; it read 0.486 / 0.634. Only then did I measure
the null: two *identical* policies, resampled to the same sizes, score 0.605 / 0.696, so 0.80 could not have been met by
any measure at these sample sizes. The stop rule I had written forbade a third definition, so no failure was classified. The
protocol did what it was meant to (no failure was read through a measure that failed validation), but twice I spent the
amendment on the wrong thing. **Lessons:** (a) simulate the statistic under "nothing differs" before fixing its threshold;
(b) an envelope built from the scripted expert describes the expert, not a success region; (c) a pooled comparison (closest
approach, never-lifted against successes) must be re-read per object before it is believed: the first pooled gap
(0.106 m against 0.066 m) was object mix, since milk and bottle sit 0.105–0.12 m from the finger midpoint even when they succeed;
(d) a reading of rendered frames is not evidence where the trace disagrees: I read "carried off the table" in frames
where the target never rose more than 1.2 cm; (e) test the branch the real data does not reach: the passing-gate path crashed on
an object that appears only as a distractor and was found only because it was given a test.

59. **A collection launch died in all 16 containers at once because the shards directory did not exist, and the tests could not have
seen it.** P3's `--collect` (forked from P2) calls `shutil.disk_usage(shards_dir)` before it creates the shard; the pilot had worked
because its directory had been made by hand, and the real launcher did not make one. `collect_shard`, `gate_shard` and `determinism`
need the robosuite image, so none of the 77 simulator-free tests, and none of the mutation checks, executed that line; the pilot
ran it only because of the manual `mkdir`. Nothing was written (the failure precedes the shard's own `mkdir`), the 16 dead containers
were removed and the launch repeated with the directory created by the launcher; the code was left alone because from `--collect`
onward it is hash-bound. **Lessons:** (a) a pilot proves only the path it was launched through: launch it the way the real run will
be launched, including every directory a launcher is assumed to make; (b) check each container's state a minute after a mass
launch (the first poll found `running=0`, which is what showed it), not after the first interval; (c) the same mutation pass found
a dead check and several unasserted ones in the merge, and a merge path whose `verify` call no test required: a check that no test
can fail is a candidate for deletion or for a test, not for trust.

60. **A confidence interval for an empty group was NaN, and the evaluation's `collect` would have crashed after the rollouts.** The P3
evaluation reports bin choice on stable placements. A stage in which nothing comes to rest in a bin (a policy that never lifts, a held-out
object below the floor) has zero of them, and `wilson(0, 0)` returned `(nan, nan)`; `write_json` refuses NaN (`allow_nan=False`), so
`collect` raised after every trial had been run. Found by the first collect test, whose fixture had trials that were never lifted; a
previously written test file had no such case, and the same branch is the one real data reaches when a checkpoint is poor. Fixed (an
empty group gives `None`, intervals clipped to [0, 1]) with tests that serialise `bin_choice([])`, `readouts([], [])` and `criteria([], [])`.
**Lesson:** a statistic over a group that can be empty needs its empty case tested through the writer, not only through the arithmetic;
this is the same class as FAILURES #58 (the branch real data did not yet reach was the one that broke).

61. **The disk budget omitted the gate scratch that `--train` re-reads, and a root-owned log then ate the margin.** P3's plan said the run needs about
61 GB at peak. `--train` re-verifies the `_preflight` and `_resumeproof` checkpoints (23 GB each, measured), so the real requirement was about
110 GB beyond the dataset, and the night script wanted 70 GiB free at launch. The machine then went from 63 to 30 GiB free overnight because
`/var/log/syslog` (root-owned, the user is not in sudoers) reached 134 GB at about 30 GB/day; the run could not resume until space was freed (the
user deleted pre-P2 datasets and a model cache) and, later, the log was truncated. **Lesson:** budget disk from what the run re-reads at every start,
not from what it writes; check what else on the machine is growing (`find / -xdev -size +1G -mmin -1500`) before deleting research data, because
deleting data would not have fixed a log that grows 30 GB a day.
62. **The checkpoint-selection rule was written by the author, not by the spec, and it decided between two readings of the same data.** The P3 plan
chose the winner on trained-object layouts only (flagged to the user, never confirmed). Held-out successes favour 126,900 (17 against 9) and
all-layout counts rank it first (83 against 77); trained-object counts (68, 68, 66, 66 of 80) are a tie in substance. **Lesson:** a selection rule
that can change the headline belongs in the spec, confirmed before the first rollout, with the tie behaviour stated; otherwise report every candidate
the alternative rule would have picked next to the winner.
63. **I advertised a code-graph feature before measuring it, and the first measurement used an ambiguous ground truth.**
On 2026-10-21 I documented `code_graph.py importers` as a way to find what a shared helper touches, after one spot check
(59 of 83 importers of `data_collection/benchmark.py`, so "71% recall"). The first benchmark then appeared to show 33% and
11% for two `scene.py` targets, but `experiments/props_scene/scene.py` and `experiments/robosuite_scene/scene.py` share a
stem, so my grep counted both modules' importers for each. With repo-unique stems the measured median recall over 14 modules
is 63% (min 0%, max 100%), and for 5 of the 14 the graph found no importer at all; precision was 100%, and the output
is no smaller than `git grep -l`. So the importer query is neither complete nor cheaper than grep. **Lessons:** (a) a
single spot check is not a measurement, and the quoted figure was the best case I had seen; (b) a grep ground truth is
only as good as its pattern, so check that the target name is unique before computing recall; (c) positive uses (file
summary 968 tokens saved per file not opened, orientation 5.3x fewer tokens than `ls`/`head`) held up, so the
graph stays, but only for those uses (`scripts/code_graph_bench.py` reproduces every figure).

64. **A pre-implementation plan froze the evaluator and then scheduled edits to that same evaluator.**
The 2026-10-30 VLA-inputs draft hashed all evaluation modules against A0, while M1–M3 later added adapters to the hashed
`adapters.py`. Its comparisons would reject those changes. The audit caught this before implementation; no run failed.
The same review found that M4a read only X-VLA's first-view/language features while predicting two camera boxes.
**Lesson:** trace the actual feature and provenance boundaries before committing to interfaces. Freeze the shared
measurement core, bind arm-specific modules independently, and test which inputs can reach each prediction head.
See [VLA_INPUTS_AUDIT_20261030.md](VLA_INPUTS_AUDIT_20261030.md) for evidence and revised plans.

Broader lessons — every "just increment a counter" or "just leave state alone on retry" assumption in the fixed-layout pipeline broke under broad_workspace retries. Rejections need explicit cleanup for every piece of shared state (LeRobot buffer + PNG dir + attempts dir semantics + admit-count invariant). And a result is only interpretable once you know what the *absence* of the treatment scores on the same protocol.

**Recurring meta-lesson — a green test suite is not evidence.** Six separate times (#10, #15, #20, #24, and twice while porting eval packages) the tests passed while the thing that actually runs was broken, because the tests exercised a *fixture*, a *constant*, the *wrong module*, or every path *except* the one the job takes. When adding a regression test, confirm it fails against the unfixed code. When forking a package, run the `symtable` undefined-name check from #24 before spending GPU time.

**Second meta-lesson — know what is hash-bound before editing.** Provenance and `SOURCE_FILES` reach further than expected: into READMEs (#17), into shared helpers used by four contracts, and into files a live run re-hashes at its final gate (#8, #17). Check membership before touching anything while a job is running.

**Third meta-lesson — measure the thing you care about.** Loss, MAE and gripper accuracy all improved while the policy became completely incapable (#21). Every cheap proxy adopted so far has eventually diverged from rollout success. Budget for real rollouts; treat proxies as debugging aids only.
